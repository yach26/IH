# AgroTwin AI — Phase-1 Working Prototype

This is the first **executable** version of the Digital Twin + Nutrient
Ledger, built directly from the frozen design in
`AgroTwin_Phase1_Data/11_Digital_Twin_Schema/` and seeded with the real
Phase-1 data (boundaries, MPKV/ICAR RDF, FCO NPK %, and the 8 synthetic
farm records). It replaces the hand-worked markdown table with real code.

## What's here

| File | Purpose |
|---|---|
| `schema_sqlite.sql` | SQLite port of the frozen Postgres schema — same tables/columns |
| `seed_data.py` | Loads real data: boundaries, crops, FCO %, MPKV/ICAR RDF, the 8 synthetic records |
| `ledger.py` | The Nutrient Ledger equations as executable functions (gap calc + product conversion) |
| `run_demo.py` | Runs everything end-to-end and writes results back into the twin |
| `data/` | Copies of the real source CSVs (`synthetic_records.csv`, `npk_composition.csv`) |
| `agrotwin.db` | The generated SQLite database — a real, queryable Digital Twin |
| `output/ledger_results.csv` | The 8-record results table, generated by code |

## How to run it

```bash
python3 run_demo.py
```

This rebuilds `agrotwin.db` from scratch, seeds it, runs the ledger for
all 8 synthetic fields, writes `nutrient_ledger_entries` and
`recommendations` rows back into the database, prints a console report,
and exports `output/ledger_results.csv`.

## What changed from the hand-worked version

1. **Banana is no longer ABSTAIN.** The earlier markdown treated banana's
   plant density as missing and abstained. It isn't missing — it's in
   `05_Crop_Calendars/four_pilot_crops.md` (2,000–2,500 plants/ha). This
   prototype uses the mid-point (2,250) to derive kg/ha from the g/plant
   RDF, and flags every banana recommendation as `DERIVED_DENSITY` so
   it's never mistaken for an exact source value.
2. **A rounding error was caught.** SYN-008's hand-calculated Urea figure
   (81.7 kg/ha) doesn't match the actual arithmetic — the code computes
   **78.3 kg/ha**. This is exactly the kind of error executable code
   catches that markdown tables don't.
3. **Confidence is computed, not asserted.** Every result carries a list
   of `flags` (e.g. `P_PROXY`, `MIDPOINT_RANGE_RDF`, `DERIVED_DENSITY`).
   Confidence is `MEDIUM` with one flag, `LOW` with two or more — this is
   a rule in code, not a label typed in by hand.
4. **Full traceability is structural, not just descriptive.** Every
   `fertilizer_recommendations` row has a `source_citation` column
   pointing to the exact file/section it came from, and every
   `recommendations` row stores its `evidence_citations` and `flags`
   alongside the plan — so "proof-carrying recommendation" is enforced
   by the schema, not just promised in prose.

## What this prototype is NOT yet

- Not an API — this is a script, not a running FastAPI service (next step
  in the build order).
- No Soil/Crop/Weather agents — the "agent" logic here is a single
  deterministic function (`ledger.run_field`). Wrapping this in the actual
  multi-agent orchestration comes after this core is trusted.
- No optimizer — DAP→Urea→MOP is a fixed rule (matches the source's
  worked example), not a multi-objective optimization yet.
- The 8 gaps in `04_remaining_gaps.md` still stand, **except** banana
  density, which this prototype resolves using data already in the pack.

## Traceability guarantee (unchanged from the frozen design)

Every kg/ha number in `output/ledger_results.csv` can be traced to:
- a specific row in `fertilizer_recommendations` (→ `06_Fertilizer_Recommendations/mpkv_icar_rdf.md`), and
- a specific row in `fertilizer_products` (→ `07_Fertilizer_Composition/npk_composition.csv`), and
- a specific `soil_test_id` (→ the synthetic record it came from).

No number in this prototype was invented.
